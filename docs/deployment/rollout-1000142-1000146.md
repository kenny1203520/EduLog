# Rollout: migrations 1000142–1000146

These migrations add single-lesson transfer cancellation, date-effective class
history, enrollment report syncing, dashboard schedule permissions and RBAC
transfer authorization. See `supabase/migrations/README.md` for each one.

The currently deployed API and web app keep working once these migrations are
applied, so the database can be migrated before the new code is deployed:

- `cancel_single_lesson_transfer` now returns jsonb. The old API ignores the
  return value.
- A direct `enrollments.class_session_id` update (the old class-transfer path)
  is recorded in the class history as a transfer effective today.
- `provision_occurrence_reports` is unchanged.

Run every command against the production database. Set the connection once:

```bash
export PGHOST=... PGPORT=5432 PGUSER=postgres PGDATABASE=postgres
# or prefix each psql/pg_dump with: docker compose exec -T db
```

## 1. Read-only preflight

```sql
SELECT
  to_regclass('public.web_extension_import_report_effects') IS NOT NULL AS has_1000141,
  to_regclass('public.enrollment_class_history') IS NULL               AS missing_1000143,
  to_regprocedure('public.get_occurrence_lesson_transfers(uuid)') IS NULL AS missing_1000142;
```

All three must be `true`. If `has_1000141` is false, apply the earlier pending
migrations first. If either `missing_*` column is false, part of this rollout
was already applied, so stop and compare the database against the files.

## 2. Backup

```bash
pg_dump -Fc -f edulog-before-1000142.dump
ls -lh edulog-before-1000142.dump
pg_restore -l edulog-before-1000142.dump | head
```

Keep the dump until the rollout is verified.

## 3. Apply, in order

```bash
for f in \
  supabase/migrations/1000142_cancel_single_lesson_transfer_chain.sql \
  supabase/migrations/1000143_enrollment_class_history.sql \
  supabase/migrations/1000144_sync_enrollment_reports.sql \
  supabase/migrations/1000145_dashboard_schedule_visibility_permission.sql \
  supabase/migrations/1000146_single_lesson_transfer_rbac_permission.sql
do
  echo "== $f"; psql -v ON_ERROR_STOP=1 -f "$f" || break
done
```

Each file runs in its own transaction, so a failing file leaves the database
as it was before that file. Stop at the first failure and keep its output.

## 4. Post-apply checks

```sql
-- Every new function is present.
SELECT name, to_regprocedure(name) IS NOT NULL AS present
FROM unnest(ARRAY[
  'public.cancel_single_lesson_transfer(uuid)',
  'public.get_occurrence_lesson_transfers(uuid)',
  'public.transfer_enrollment_class(uuid,uuid,date)',
  'public.sync_enrollment_reports(uuid,integer,date,boolean)',
  'public.prepare_repeatable_single_lesson_transfer(uuid,uuid,uuid)',
  'public.repair_single_lesson_transfer_report(uuid,uuid)',
  'private.is_blank_occurrence_report(public.occurrence_reports)'
]) AS name;

-- Dashboard permissions are seeded.
SELECT key FROM public.permissions WHERE key LIKE '%dashboard.schedule.all';

-- Every enrollment with a class has an open history segment.
SELECT
  (SELECT count(*) FROM public.enrollments WHERE class_session_id IS NOT NULL) AS enrollments_with_class,
  (SELECT count(*) FROM public.enrollment_class_history WHERE effective_to IS NULL) AS open_segments;

-- Previous classes inferred by the backfill: review each row.
SELECT student.name AS student, session.name AS class, history.effective_from, history.effective_to
FROM public.enrollment_class_history AS history
JOIN public.enrollments AS enrollment ON enrollment.id = history.enrollment_id
JOIN public.students AS student ON student.id = enrollment.student_id
JOIN public.class_sessions AS session ON session.id = history.class_session_id
WHERE history.effective_to IS NOT NULL
ORDER BY student.name, history.effective_from;
```

`enrollments_with_class` and `open_segments` should match. The last query
should list only students who really changed class. A wrong segment makes the
student appear in the old class on those dates. Fix it with a targeted UPDATE
or DELETE on `enrollment_class_history`, not by restoring the backup.

## 5. Rollback

Only if the checks fail and the data cannot be fixed forward. Restoring the
dump discards every write made since the backup:

```bash
pg_restore --clean --if-exists -d "$PGDATABASE" edulog-before-1000142.dump
```

Prefer a reviewed forward migration over a restore.
